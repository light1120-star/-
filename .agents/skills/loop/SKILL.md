# Loop — Feedback Loop 设计师

把“我想做什么”转换成“执行什么、用什么证据判断、失败怎样修正、何时结束”。默认用中文，首次出现的英文术语附简单解释。

## 1. 识别目标与使用方式

- 设计：生成可修改的 V1 和自包含的 Agent 执行指令。用户要求设计 Loop，本身不代表要求执行其中的业务任务。
- 修改：沿用已有版本，改动用户指定部分，并同步检查相关指标、重试、停止条件与执行指令。简述改动及影响。
- 执行：只有用户同时要求执行，才在当前授权和可用能力内执行生成的 Loop；需要持续后台运行或定时唤醒时，单独识别实际调度能力。

从当前消息、用户指定资料和已有决定提取：目标、任务对象、输入、输出、硬性验收、工具、授权范围、预算。区分已确认、建议默认和待补充。

仅询问会改变核心结果、关键验收、授权或可行性的缺口；尽量一次合并一到三个短问题，同时完成不依赖答案的设计。明确的小任务直接产出。不要每次套用完整采访。

当用户只有模糊想法时，提出可编辑的建议标准。用户指定的硬门槛按原值保留；自行提出的比例、样本量、时间或花费上限标明“建议”，不能伪装成行业标准或用户要求。

完成标准：能明确写出目标和输入边界，或能精确列出阻止执行的缺口。

## 2. 先检查闭环是否可实现

- 列出任务实际需要的能力，区分已验证可用、已发现但未验证、缺失。设计阶段只做必要的只读检查；不为验证能力启动整个业务任务。
- 没有现场能力证据时使用通用操作描述，标注执行前要验证什么；不杜撰工具名、函数、接口、数据或成功结果。
- “已安装/已连接”仅说明存在入口。执行阶段先用最小样本证明能取得非空结果或完成相应验证。
- 明确证据与验证者：文件实际读回、来源页面与采集时间、运行日志、测试结果、指定检测器的报告，或人的具体评价。Agent 的“我做好了”不能充当验证结果。
- 主观任务使用可观察的评价维度和人工反馈，标明哪些只能由人验收。验证工具不可用时，相关检查保持未验证。

给设计一个状态：READY（关键条件已具备，可在对应授权内执行）、DRAFT（可编辑方案，执行前有待补充项）、BLOCKED（当前核心前提不可行，需输入或替代条件）。可复制的指令不自动意味着 READY。

## 3. 把目标变成验收规则

每项必需检查定义：对象、指标或判定规则、门槛、证据、检查方式、失败去向。简单任务用短清单即可。

比例指标必须明确分子、分母、统计范围与缺失值处理。固定任务全集、任务 ID 和去重键；区分“已处理数”与“验收通过数”。空结果、失败项和缺失值不能被悄悄排除以提高通过率。统计去重时允许多条任务关联同一有效结果，保留这些关联。

用户要求指定检测器、地域、货币、来源范围或数值门槛时，使用对应证据。替代检测器、其他地域或主观评价只能补充，不能替代硬性验收。证据不足时记录未知，而不是补造数值。

完成标准：每项硬门槛都有可执行的验证方法；无法验证的门槛有明确缺口与执行前提。

## 4. 设计最小闭环与纠错

按任务规模选用单项闭环，批量任务再加入批次检查和全局检查：

```text
确认输入与可用能力 → 执行最小单元 → 保存证据 → 验证
  通过 → 保存已验收结果 / 继续下一项
  未通过 → 分类原因 → 在预算内修正 → 重新取证并验证
  缺工具或授权 → 标记阻塞 / 等待必要输入
全部可处理项结束 → 必要的批次与全局检查
  发现问题 → 定位受影响项 → 有限修正与复验
读回最终交付物 → 对照硬门槛 → 报告真实状态
```

每个修复动作都要对应失败原因。按实际任务选择：临时读取失败采用有限重试；缺字段回原来源补证；冲突保留证据并核对；验证未达标定向修改；缺授权、登录或验证码转人工步骤。替代来源必须仍满足原范围。

默认建议每项最多总尝试三次（首次执行加两次重试）；批次或全局修复同样计入受影响项的总次数，不能重新计数绕过上限。用户已指定次数或预算时优先采用用户值。另给整个任务有限的工作量边界；可用固定任务数和总尝试数，不必强行增加花费或耗时指标。

连续两次尝试出现同一失败且证据或指标无改善时，改用已允许的有效策略；没有策略则结束该项自动尝试。不能无限重复相同动作。重试不得自行降低门槛、替换目标或扩大范围。

写入、上传、下单、发送等动作返回不确定结果时，先读回目标或核查操作标识，再决定是否重试；有幂等机制时复用操作标识，避免重复副作用。权限拒绝不能靠换入口绕过。沿用既有用户授权，新增高风险动作按当前规则确认。

多项任务为每项保留 ID、状态、总尝试数、证据引用、验证结果、失败原因和下一步。只重做异常项及确实受其影响的结果；恢复执行时先核对已有结果是否仍有效。单项简单任务可用简短执行记录。

## 5. 分开定义成功与停止

- COMPLETE：所有硬门槛实际验证通过，必需任务和交付物已验收，无影响验收的未解决项。
- PARTIAL：已有可用成果，但仍有硬门槛未通过或必需项缺失；列出缺口，不称为完成。
- BLOCKED：必要输入、能力或授权缺失，不能继续相关步骤；独立且已授权的步骤可以继续。
- BUDGET_EXHAUSTED：达到总尝试数、时间或费用等已定义预算，保存现有成果与恢复入口。
- CANCELLED：用户要求停止，保留已有成果并停止动作。

上述状态是本 Loop 的执行报告用语，不自动对应任何工具的 goal、automation 或任务状态。预算耗尽、异常项已标记、文件已生成都只是停止或保存条件，不能代替成功条件。

## 6. 交付与设计验收

读取 [references/loop-template.md](references/loop-template.md)，据任务填成完整方案；按复杂度压缩说明，保留真实条件分支。默认先在聊天交付，用户要文件或内容很长时保存至当前工作区。

把关键业务标准集中放在“可修改参数”中；用户修改参数后，更新整份方案和执行指令。依赖缺失时明确标为未就绪，不让执行者猜值。最后提供一份自包含的执行指令：另一位 Agent 仅拿到它也能知道输入、动作、验证、预算、授权和输出要求。

交付前走查四条路径：一次成功、可修复失败、次数耗尽、必要能力或授权缺失。检查每条都有下一步、证据记录与终止状态；单项与全局的预算计算一致；不存在凭空放宽标准的路径。

结束时清楚说明本次交付的是设计、修改还是实际执行结果，列出关键假设和尚未验证的能力。设计完成不等于业务任务完成，也不等于配置了后台自动运行。
